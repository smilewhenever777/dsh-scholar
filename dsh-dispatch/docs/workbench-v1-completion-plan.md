# dsh-dispatch 工作台完整版本补充方案

> 方案日期：2026-09-23。本文定义后续交付与验收，尚未表示这些功能已实现。执行次序以阶段和验收门槛为准；`0.8`、`0.9`、`1.0` 等版本号在发布前再确定。

## 1. 完整版的含义与边界

**交付目标**：在 DSH 内完成一个本机单人使用的 AI 团队工作台。用户可以围绕项目管理任务，把任务分派给 Agent 或顺序小队，手动启动或用本地定时规则触发执行，读懂每次执行的全过程和交付物，讨论并人工验收。没有安装 trajectory 也能完成全流程；trajectory 只是可选关联，原派发 API 和旧历史继续可用。

**保持的产品约束**：分派不触发运行；一次只有一个全局执行槽；普通任务和小队都不隐式排队；工作台继续使用现有受控读取、报告写入、进度工具；完成 Run 不等于完成任务，只有人工接受才能进入 `done`。自动化规则是用户主动启用的例外，它只在预定时刻尝试启动，忙时记录跳过，不留下等待队列。服务端始终决定工作区、模型和工具白名单，客户端不能放宽权限。

**不把“完整”误解为逐项复制 Multica**。Multica 的公开模型明确区分长期 Issue 和单次 Run，执行日志在任务侧栏，完整 transcript 单独展开；其小队由 leader 运行后按需分派，而先前确定的 DSH 方案是固定顺序的本地小队。两者可以借鉴信息结构，不能当作同一执行语义。[Multica Runs](https://multica.ai/docs/tasks)、[Multica Squads](https://multica.ai/docs/squads)。多用户角色、云端 runtime、移动端、聊天机器人、外部 webhook、自动评论触发、leader 自主路由均不列入本地 v1.0 的完成条件；若以后需要，应另立需求和安全边界。

## 2. 当前基线与缺口

以当前工作区代码为基线，`dsh-dispatch` 包版本为 `0.7.1`；下表描述功能位置，不代表本轮重新完成了端到端验收。上一轮体验观察与证据见 [工作台体验报告](workbench-ux-review-2026-09-23.md)。

| 能力 | 当前状态 | 完整版缺口 |
| --- | --- | --- |
| 项目、Agent、任务 | 已有独立存储、CRUD、revision 冲突检查、项目路径校验 | 项目目标/进度/活动、Agent 角色描述与能力说明、适合实际使用的选择与筛选 |
| 任务与 Run | 手动启动、单槽、幂等、取消、重启对账；一任务多 Run | 任务页重新布局；专用 Run 阅读视图；每次 Run 的配置快照和更清晰的触发来源 |
| 讨论与验收 | 评论、退回、人工接受已有 | 交付物与验收动作靠近；验收明确绑定具体 Run；任务状态与历史 Run 状态同时清楚可见 |
| 执行记录 | 通过 `sessionQuery` 读取子会话事件并分页显示 | 长记录的过滤、定位、顺序切换、阅读位置保持、性能与冷重启验证 |
| 小队 | 未实现 | 固定顺序、多 Agent 独立 Run、失败暂停、恢复与冷启动对账 |
| 定时自动化 | 未实现 | 本地规则、触发审计、时区与停机语义、忙时跳过、去重 |
| 旧历史 | 只读呈现，不伪装为已验收任务 | 在新导航中保持易找，升级回归不能改变其语义 |

当前数据结构的关键事实：`WorkbenchRoot` 仍是 `schemaVersion: 1`，项目只有名称与路径，Agent 只有名称、指令、模型和工具列表，任务用 `assigneeId` 指向单个 Agent，时间线保存在任务数组中；工作台总览一次返回项目、Agent 和任务。后续新增小队、规则和大量活动时必须做可回滚迁移与分页，不能仅在页面上叠组件。

## 3. 信息架构与主流程

### 3.1 导航和页面职责

| 页面 | 用户在这里完成的事 | 首屏必须看见 |
| --- | --- | --- |
| 总览 | 判断现在要处理什么 | 正在运行、待验收、受阻、最近活动与下一步入口；计数可点并带筛选 |
| 项目 | 建立范围并浏览任务 | 目标、工作区、进度、最近更新、看板/列表切换、创建任务 |
| 任务 | 定义目标、分派、讨论、验收 | **任务状态**、分派对象、最近 Run 状态、主动作、交付摘要、验收条件 |
| Run | 阅读一次执行 | Agent、触发方式、状态/耗时、摘要、报告与证据、完整事件流 |
| Agent | 管理可复用执行身份 | 角色描述、模型、工具能力、最近任务/Run、配置入口 |
| 小队 | 配置固定顺序的 Agent | 步骤顺序、每步职责、最近小队执行、暂停原因 |
| 自动化 | 管理本地定时规则 | 启停、时区、下次触发、目标模板、最近触发结果 |
| 旧历史 | 回看旧派发记录 | 来源标识、只读说明和原记录入口 |

任务详情采用“中央任务活动/交付 + 右侧属性、Run 与验收”布局；窄屏把右侧内容变成有明确入口的折叠区。看板卡片只显示状态、负责人、下一步和最近更新时间，点击进入完整任务页。运行中用页头短状态和最近 Run 入口持续可见；完整消息和工具记录放在 Run 视图，避免任务页内外双重长滚动。视觉参照 Multica 的信息层级和留白，但使用 DSH 自有文案、组件、颜色与图标，不照搬其 UI 文件。[Multica Runs](https://multica.ai/docs/tasks)、[Multica Issues](https://multica.ai/docs/issues)。

### 3.2 任务、Run 与验收的状态语义

```text
项目 → 创建任务(todo) → 指定 Agent/小队(仍为 todo)
    → 手动运行或启用的自动化触发 → in_progress
    → 成功：in_review → 人工接受：done
                            └→ 退回(附意见)：todo → 新 Run
    → 失败/受阻：blocked → 修复后重跑(保留旧 Run)
    → 取消：静止确认后 todo
```

- “Run 执行完成”只描述一次执行；“任务已完成”只描述人工验收后的任务。列表、标题、活动流和历史记录使用一致的两个标签。
- 审核操作传入最新待审 Run 的 ID 与任务 revision；若执行、重分派或另一个审核已改变任务，返回 409 并让用户重新确认。历史审核事件不能冒充当前任务状态。
- 重新运行永远追加 Run，不覆盖旧会话、报告、证据或决定。Agent/Profile 改动只影响下次 Run，详情展示本次启动时的配置摘要。
- 执行中修改目标或验收条件仍须先取消或接管。取消必须等现有静止确认，不能因 UI 乐观更新直接释放执行槽。

## 4. 分阶段交付

### 阶段 A：任务和 Run 的阅读体验达到日常可用

**实现内容**

1. 把任务抽屉改成工作台内可定位、可刷新的完整任务页；保留看板快速入口。页头始终显示任务状态、最近 Run 状态和下一步动作。Run 历史从第 1 次就可见，当前运行置顶，旧 Run 按时间折叠。
2. 将任务活动组织为“用户评论、Agent 交付、验收决定”的主线；进度和系统事件按摘要收起。交付卡先列结果、文件、未完成项，再提供报告全文与安全预览。验收条件和接受/退回按钮紧邻交付物。
3. 建立专用 Run 阅读视图：事件时间线、Agent 消息、工具调用与结果、错误、报告、证据；提供“只看关键事件/全部”“按类型筛选”“最新/最早优先”“跳到最新”。展开工具卡才读取或显示长参数。实时增量在用户滚离底部时不抢滚动位置。
4. 总览和列表增加“需要我处理”排序、状态/项目/Agent 筛选与空状态引导；按钮的文案对应实际动作，如“分派”“运行”“继续验收”。关键动作提供键盘访问与清楚的焦点状态。
5. 为 1280、1024、768 像素和 200% 缩放设置布局断点；验证主动作、Run、证据、评论在不同宽度可达，不产生嵌套无边界滚动。

**交付门槛**：在 3 个任务、2 个 Agent、1 条 50+ 事件 Run、1 条 500+ 事件 Run 中，用户能从总览两次点击内进入待验收任务；无需滚过完整 transcript 即能看到交付与审核；筛选和刷新后仍能返回原 Run；键盘可完成主要流程。长记录使用按序分页或虚拟列表，不能让全量事件进入首屏 DOM。运行中追加事件的顺序、去重和滚动行为有自动化覆盖。

### 阶段 B：补全项目与 Agent 信息，并完成数据升级

**实现内容**

1. 项目增加目标/说明、可选归档状态、基于任务状态计算的进度和最近活动；工作区路径使用宿主提供的选择能力（若宿主没有该能力，则保留输入并即时展示真实路径校验结果）。项目页可按状态、更新时间和分派对象找任务。
2. Agent 增加独立的**展示描述/职责**，与会进入提示词的 instructions 分开；以人话列出受控读取、报告写入、进度等能力和限制。显示最近 Run、受阻原因与操作入口；不在缺乏宿主证明时显示“在线”。
3. 每次启动保存不可变配置快照：目标/验收条件、项目路径、Agent ID/名称、模型、最终工具白名单、触发来源，以及所属小队步骤或自动化规则引用。快照只用于审计和展示，不作为客户端可编辑的权限来源。
4. 存储从 v1 迁移到下一 schema：写前备份、全量校验、临时文件加原子替换；失败维持只读并提示备份路径。旧任务 `assigneeId` 明确迁移为 `assignment: { kind: 'agent', id }`；旧 Run 的字段缺失以“旧版未记录”显示，不回填猜测值。旧派发记录保持只读且不自动变成任务。
5. 将任务列表/活动/评论做服务端分页或游标；总览返回计数和少量最近项，项目页按需加载。明确存储容量、审计保留和压缩策略，在不删 Run/审核事实的前提下控制前端与 API 负载。

**交付门槛**：用 v1 fixture、损坏 JSON、写入中断、并发编辑和旧历史样本测试升级。升级前后项目/Agent/任务/Run 数量与 ID 一致；失败只读且原件与备份可恢复；10k 任务与 500 事件 Run 的列表/阅读性能在隔离实例测量并记录实际耗时，不以臆定阈值宣布通过。

### 阶段 C：固定顺序的小队

**产品规则**

小队由用户配置 2 个或更多 Agent 和顺序职责。用户把任务分派给小队后仍需点击“运行”。每一步产生一个独立 Run，后一步收到前一步的交付摘要与证据引用，但只允许访问自身 Agent 被服务端批准的工具。全部步骤成功后任务才进入 `in_review`；任一步受阻或失败，小队停在该步，任务进入 `blocked`。恢复时默认重跑失败步骤并创建新 Run，绝不复用或改写旧 Run。跳过步骤须另行明确操作和审计；首版可以不提供跳过。

**实现内容**

1. 新增 `Squad`（名称、说明、有序步骤、各步 Agent ID/职责、revision）和 `SquadExecution`（taskId、步骤快照、当前下标、状态、每步 Run ID、暂停原因）。小队配置改变不修改已启动的小队执行。
2. 将当前目标适配器的“成功即 `in_review`”扩展为编排感知转移：中间 Run 成功保持 `in_progress`，只有最后 Run 成功进入 `in_review`。失败进入 `blocked` 并停步；取消经静止确认后回到可重启状态。每次状态转移与下步启动采用持久操作 ID，避免回调和重启重复创建 Run。
3. 所有步骤共享现有单执行槽；一步结束后仅在槽空闲时自动接续。若其它手动任务抢到槽，小队变为 `paused_busy` 并显示“继续”动作，不形成后台等待队列。浏览器关闭不影响已运行步骤，宿主重启后根据派发记录和执行租约进行对账。
4. 小队详情显示步骤与最近执行；任务右栏显示当前步骤、已完成步骤的 Run 和交付、暂停原因与“继续/取消”。每一步 Run 都能进入同一专用 Run 视图。

**交付门槛**：2 步和 3 步成功链均产生对应数量、不可覆盖的 Run；首步失败/阻塞时绝不启动后一步；中间步骤取消、双击继续、Agent 配置改动、槽竞争、宿主在“前一步结束/后一步启动”边界重启，都不会丢步骤或重复执行。人工验收只在最后一步成功后出现。

### 阶段 D：本地定时自动化

**首版规则**：用户保存一个任务模板（项目、标题、目标、验收条件）和执行对象（Agent 或小队），设置本地时区、定时表达式/界面选项并启用。每次到点尝试**创建一条新任务并启动**，避免复用已验收或受阻任务；新任务及 Run 标出规则和计划触发时间。规则只在用户明确启用后运行。禁用立刻阻止未来触发，不停止已开始的 Run；需要停止时使用现有取消入口。[Multica Autopilots](https://multica.ai/docs/autopilots) 可作为“规则 + 触发审计”的交互参考，但 DSH 首版不提供外部 webhook 或多运行模式。

**执行与故障语义**

- 现有 `dispatch.start()` 必须先读到任务，随后才在派发存储里原子占槽。为了严格做到“忙时跳过且不创建任务”，先扩展派发内核，提供带过期与恢复语义的**条件入场令牌**：原子检查/预留全局槽，成功后按确定性 taskId 创建任务，再由同一令牌启动 Run。创建或启动失败时释放令牌并保留可追踪审计；不能靠前端先查询“空闲”来避免竞争。
- 触发以 `(ruleId, scheduledAt)` 为唯一键，先持久记录 `TriggerAttempt` 再调用启动；重复调度、双进程或重启对账不得产生两条任务/Run。记录 `planned`、`started`、`skipped_busy`、`skipped_invalid`、`failed`、`missed_offline` 及原因、任务和 Run 引用。
- 全局槽忙时写入 `skipped_busy`，不创建等待任务，也不补跑；项目路径或 Agent 无效时写入 `skipped_invalid`，页面给修复入口。若任务已创建但启动失败，保留可见任务并把尝试标为失败，不能留下找不到的孤儿记录。
- 宿主停机期间错过的时间点不执行。重启时把规则游标推进到下一未来时间，并写一条有时间范围/次数的 `missed_offline` 审计摘要；不为每个错过点无限生成记录。夏令时/时区变化用明确的时间库语义和“接下来 5 次触发”预览校验。
- 规则有 revision、最近触发、下次触发和独立启停；每次尝试保存规则与任务模板快照。调度器只有一个持久所有者，读到损坏/只读存储时停止触发并在页面显示原因。浏览器是否打开不影响宿主内调度。

**交付门槛**：按分钟/日/周规则测试到点、禁用、更新竞争、忙时跳过、时区与夏令时、宿主停机、启停重启和“写审计后崩溃”恢复。对每个计划时刻最多一条尝试记录、最多一条新任务和一条首 Run；停机错过的触发没有补跑；每个未运行的原因都能从 UI 查到。

### 阶段 E：v1.0 稳定化与发布

1. 安全复核：所有 `/dispatch/workbench/*` 读写端点保持 loopback/Host/同源 Origin 限制；工作区路径、证据预览、会话事件只按当前 Run 授权范围读取；系统提示词和推理内容不进入前端。新增小队/规则 API 仍要求 revision，冲突返回 409；服务端对每步 Agent 的工具白名单做交集而非并集扩权。
2. 数据与并发复核：旧/新 schema、备份失败只读、PID/锁恢复、并发启动、双击取消、冷恢复、重复计划触发和运行时定期写入。Run/验收/触发审计按 ID 可追踪且不会被 UI 计算覆盖。
3. 可用性复核：无 trajectory 的隔离宿主走完整流程；真实模型长 Run、两次运行的同任务、小队三步、停机再开、自动化一次触发；1280/1024/768 像素与 200% 缩放、键盘和屏幕阅读器基本语义；错误与空状态有可执行的下一步。
4. 发布复核：更新 README、迁移说明、API 与状态表、变更日志、版本及锁文件。运行 `dsh-dispatch` 测试、相关插件回归、仓库 `check:release`；构建后检查 `npm pack --ignore-scripts` 内容与实际 DSH 宿主加载版本，必要时重启宿主和客户端。记录自动化和小队在真实宿主的测试回执，而非只看 mock 测试通过。

## 5. 数据与接口设计约束

建议在阶段 B 前先冻结一次数据协议评审。下表是所需的最小新增实体，不要求照搬 Multica 后端表结构。

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| `Project` | `goal`、`description`、`archivedAt?`、原有 `root/revision` | 根路径仍由服务端验证；进度从任务推导，不手写两套状态 |
| `AgentProfile` | `description`、原有 `instructions/model/toolAllow/revision` | 展示描述不注入提示词；Run 保存启动快照 |
| `WorkTask` | `assignment: agent|squad`、`runIds`、`reviewEvents`/活动游标 | 编辑竞争 409；只有人工接受进入 `done` |
| `DispatchRecord`/Run | `taskId`、触发来源、配置快照、步骤/规则引用、现有会话与证据引用 | 每次执行独立、不可覆盖；旧 Run 可读取且缺字段可解释 |
| `Squad`/`SquadExecution` | 有序步骤、步骤快照、当前步骤、Run ID 集合、状态 | 一步一个或多个重试 Run；最多一个当前执行步骤 |
| `AutomationRule`/`TriggerAttempt` | 模板、时区、schedule、启停/revision、游标；计划时间、结果和引用 | `(ruleId, scheduledAt)` 唯一；停机不补跑；忙时不排队 |

建议保留当前 API 前缀，按资源追加 `/projects/:id`、`/agents/:id/runs`、`/squads/*`、`/squad-executions/*`、`/automations/*`、`/automations/:id/attempts`。现有任务/Run/事件路径继续兼容；前端通过游标请求任务、活动和会话事件。所有 PATCH/启动/审核/继续操作带 `expectedRevision` 和幂等键；实际资源以服务端快照和 ACL/工具上限为准。新读 API 不泄露宿主绝对路径以外的敏感会话内容，文件预览必须复用现有路径围栏和格式白名单。

## 6. Multica 复用策略

用户希望复用官方实现，实施前需要逐文件审查，而不是把整个仓库当作普通 Apache 2.0 代码库。当前官方许可证包含 Apache 2.0 条款和额外的 Part I 条件；其 UI 目录的衍生使用涉及品牌/版权展示及再分发要求。[Multica LICENSE](https://github.com/multica-ai/multica/blob/main/LICENSE)。

| 候选 | 处理方式 |
| --- | --- |
| Issue/Run 分离、项目/Agent 导航、执行日志信息层级 | 借鉴产品模型，按 DSH 状态机独立实现；保留原文档引用 |
| 官方非 UI 的纯函数或小型协议实现 | 实施时固定上游 commit，逐文件记录许可证、依赖、接口和可移植性；满足附加条件、保留 NOTICE/归属后才考虑移植与测试 |
| 官方 UI 组件、样式、图标和品牌素材 | v1 不复制；用 DSH 自有界面达到相同的信息清晰度。若未来确要移植，先获得适用授权或严格满足许可证条件 |
| `dnd-kit` 等独立 MIT 依赖 | 延续现有独立依赖和许可证记录，不必通过 Multica 仓库复制 |
| 官方 leader 路由小队/云端队列/Go 服务代码 | 与本地顺序小队、TS/Cordis 宿主和单槽语义不匹配；只参考行为文档，不直接接入 |

每次实际复用提交附一张简短清单：上游路径/commit、许可证与 NOTICE、引入文件、依赖、替代方案、适配测试、用户界面是否出现上游标识。无合格候选时独立实现，不为了“复用”增加跨语言服务或云端运行依赖。

## 7. 最终验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 不装 trajectory，从零使用 | 创建项目/Agent/任务 → 分派不自动跑 → 手动运行 → 看消息、工具、报告、证据 → 接受或退回，全部在 DSH 工作台完成 |
| 一任务两次执行 | 退回后再运行生成新 Run；两个会话、报告和审核事件都可读；任务状态与历史状态不混淆 |
| 并发与恢复 | 重复点击、两个浏览器 revision 冲突、取消后静止确认、宿主冷重启，对应 Run/任务状态唯一且可解释 |
| 小队 | 每位 Agent 独立 Run；中途失败暂停；继续重跑当前步骤；末步成功才待验收；槽竞争不隐式排队 |
| 自动化 | 启用后按本地规则触发；忙时跳过并审计；停机错过不补跑；重启/重复触发没有重复任务 |
| 长记录与可访问性 | 50/500 事件可定位关键过程；报告和文件预览安全；窄屏/放大/键盘可完成核心操作 |
| 安全和旧数据 | 跨源/非本机请求拒绝；路径越界拒绝；旧记录只读；迁移失败可由备份恢复且存储保持只读 |
| 发行物 | 测试与 release check 通过、打包内容正确、真实宿主加载新版本并留存端到端回执 |

**阶段放行顺序**：A 的任务/Run 体验达到可读、可审，B 的 schema 和分页完成且可恢复，再叠加 C 的小队和 D 的定时触发，最后 E 做跨能力回归。每阶段结束要给出实际构建、测试、真机流程和未通过项；仅有页面截图或单元测试通过，不算完成该阶段。
