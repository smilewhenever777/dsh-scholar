# dsh-dispatch v0.10.0 当前版本审计（2026-09-24）

## 结论与范围

单 Agent 的项目 → 任务 → 手动运行 → 查看记录 → 人工验收闭环已经可用。小队与自动化已经有模型、接口和基础页面，但尚不适合无人值守：步骤交接、定时语义、崩溃恢复仍有可导致目标变更、重复执行或漏执行的缺陷。UI 的主要问题是错误的分派状态和缺少小队执行视图。

本次核对 HEAD `5dc63ff`、包版本 `0.10.0`。`dsh-dispatch` 的 89 项测试、仓库 `npm test` 和 `npm run check:release` 均通过。在线宿主的只读工作台接口返回 200，显示版本 0.10.0 功能已加载。未在在线宿主创建任务或启动模型。浏览器访问需要 DSH Web 鉴权，未得到已登录截图，因此视觉布局判断来自组件和样式代码；下面明确区分隔离复现与静态路径分析。

## P0：先修执行正确性

| 问题 | 证据与影响 | 修改建议 |
| --- | --- | --- |
| 小队两步之间任务可被编辑 | **隔离复现**：第一步完成后任务为 `in_progress` 且 `owner` 被清空，`updateTask` 仍允许修改标题。`src/workbench/target.ts:95-117`、`src/workbench/service.ts:171-203`。验收标准、分派对象也可被改动，下一步可能使用另一份任务合同。 | 在有 `running` 的 SquadExecution 时锁定目标、验收条件、分派和状态；取消/接管时先把小队执行推进终态。领取时还应核对小队执行 ID 和预期步骤。 |
| 小队接续的启动幂等键包含时间戳 | **代码路径确认**：`src/workbench/service.ts:385-403` 先 `dispatch.start`，后写 `currentStep/runIds`，幂等键含 `Date.now()`。两次操作之间崩溃后，重启接续会以新键再发同一步。首步也存在创建执行记录与关联 Run 的间隙（:263-295）。 | 对每个执行和步骤使用固定键；先持久化 `starting` 意图和步骤标识，恢复时按固定键查询/重放并核对绑定 Run，写入关联后才推进步骤。增加断点故障注入测试。 |
| 自动化配置的时区不起作用 | **隔离复现**：相同 `0 9 * * *` 在 `UTC` 和 `Asia/Shanghai` 的 `nextTriggerAt` 完全相同。`src/workbench/automation.ts:266-291` 用宿主本地 `Date` 计算，未读取 `timezone`。用户可能在错误时间触发任务。 | 用验证过的 IANA 时区计算下次触发；明确 DST 跳过/重复的规则，并对 UTC、上海及 DST 切换做测试。修复前不要把时区输入展示为已生效。 |
| 自动化已有 `planned` 记录时无法恢复 | **代码路径确认**：`src/workbench/automation.ts:173-210` 在 `planned` 落盘后启动任务；同一 `(ruleId, scheduledAt)` 已存在就直接返回。崩溃在两者之间会留下永久 `planned`，后续 tick 不会启动或收尾。 | 将 attempt 做成可对账状态机；启动前持久化确定性任务 ID/幂等键，重启后查 Run/任务并收敛到 `started/failed/skipped`。 |
| 自动化写入没有被真正等待 | **代码路径确认**：`src/workbench/automation.ts:246-260` 两个 `async` 方法调用 `store.mutate` 却不 `return/await`。上层 `await` 会提前结束，写入失败也可能变成未处理拒绝；下一轮 tick 可看到旧游标。 | 返回 `await this.store.mutate(...)`，并让 tick 串行、显式记录调度失败。 |

## P1：功能和状态缺口

| 问题 | 证据与影响 | 修改建议 |
| --- | --- | --- |
| 小队没有显式交接内容 | `SquadStep.responsibility` 只存储和展示；`src/workbench/target.ts:22-26` 给下一步的仍只是任务描述/验收条件，`service.ts:385-393` 不传前一步摘要、报告或证据。小队顺序执行不等于协作交接。 | 为每步记录交接摘要、报告引用和证据；下一步提示词带经过裁剪的前一步交接包，并在执行详情显示交接来源。 |
| 小队启动失败被静默自动重试 | `src/workbench/service.ts:405-407` 捕获全部错误后保持 `running`，30 秒后重试。容量忙、工作区占用、模型配置失效混在一起；页面无暂停原因或手动继续。 | 忙时设 `paused_busy` 并给“继续”动作；永久配置错误设 `paused_failed`。记录失败原因和尝试次数，避免隐式排队。 |
| 自动化可留下孤立任务 | `src/index.ts:143-151` 先建任务后启动；若运行槽/工作区或配置在启动时拒绝，attempt 仅记 `failed`，没有任务 ID 可从自动化列表进入。崩溃时还可能再次创建同一计划时刻的任务。 | 将自动生成任务与 attempt 建立固定 ID 关联；先做项目/Agent/工作区可用性校验，失败任务在审计中可见且可处理。 |
| 自动化规则校验和版本约束不足 | `src/workbench/automation.ts:78-125` 没有验证时区、项目/Agent 真实存在、模板更新后的必填字段；`Number(raw.expectedRevision)` 非整数时跳过版本检查。`src/workbench/squad.ts:101-103` 同样允许缺失 revision；DELETE 也无版本参数。 | 创建/更新做完整校验；修改与删除都强制正整数 `expectedRevision`，冲突返回 409。 |
| 停机错过的判断只是两分钟阈值 | `src/workbench/automation.ts:152-165` 将逾期两分钟以上都记作 `missed_offline`，不足两分钟则执行。重启短于两分钟会补跑，长时间事件循环阻塞会被误判为停机。 | 持久化宿主启动时间和上次 tick，按真正在线区间判断；明确边界时间点，只记录错过而不补跑。 |
| 稀疏合法 cron 被禁用 | **隔离复现**：从 2025-03-01 计算 `0 9 29 2 *` 得到 `0`。`src/workbench/automation.ts:269-291` 只搜索 400 天，下一次闰日可能超过窗口。 | 至少覆盖一个完整公历 400 年周期，或使用可靠的 cron 解析器并显式报告无效规则。 |
| 卸载后小队定时器仍存活 | `src/index.ts:179-195` 的 `squadTimer` 没有在 `dispose` 清除，插件重新加载可能产生重复检查。 | 将 timer 保存在外层并在卸载时 `clearInterval`，同时对 `ensureSideServices` 并发初始化加单例 Promise。 |
| 存储失败时内存先行改变 | `src/workbench/store.ts:238-239` 先替换 `this.root` 后 `persist`；落盘失败进入只读时，当前进程可看到未持久化的修改，重启后消失。`init` 每次启动还重写 v2 文件和 `.bak`。 | 成功落盘后再交换内存根；只在实际迁移时重写文件；校验 Squad/Automation 集合并增加 v1→v2 和写失败回归。 |

## 与已定计划的差距及修复顺序

1. **先保证执行不会错跑或重跑**：小队交接锁、确定性步骤键与恢复、自动化时区与 attempt 对账、真正等待写入。
2. **补齐协作与审计**：每步交接包、暂停原因/继续动作、自动生成任务关联、严格 revision/模板校验。
3. **消除页面误导**：统一 `assignment` 字段，完成小队执行页面，修复弹窗和自动化文案，再优化 Run 阅读布局。
4. **补验证**：隔离宿主的多步骤小队、时区/DST、崩溃断点、错过触发、自动化任务关联及已登录界面截图；现有 `scripts/e2e-workbench.mjs` 主要覆盖单 Agent 闭环，不覆盖小队与自动化。

另外，README 顶部 `:14,18` 仍写“全局单槽、仅第一里程碑、后续才做小队/自动化”，与 `:68-75` 和当前默认并行 3 个任务冲突。应更新为 v0.10.0 实际行为，并确认“跨工作区并行”是否是新的产品决定。
