# dsh-dispatch 工作台体验报告与界面优化建议

日期：2026-09-23  
评估对象：仓库 `dsh-dispatch` v0.6.0 工作台（包含当前工作区两处尚未提交的交互修正）  
目标：更舒服、更简单、更高效；让任务状态、执行过程和交付结果直观、明确，并借鉴 Multica 的工作方式与信息层次。

## 1. 评估依据与边界

我在本机 DSH 的 1280×720 浏览器视口中走查了总览、看板、列表、一条真实任务的详情、已有 Run 的结果概览、执行过程、原始记录及 Agent 配置入口。样本为 **1 个项目、1 个任务、1 次已结束的 Run**。该 Run 有 18 条原始事件，执行过程合并后为 9 条活动，包含 3 条 Agent 消息、工具调用、约 2.4 万字的单次写入参数、报告和 2 个本地交付文件。我没有启动新的模型 Run，因此对实时跟随、取消和多 Run 对比仅做了代码检查，不能视为真机体验结论。

官方对照依据是 Multica 当前公开的 [任务页面与运行中状态截图](https://multica.ai/docs/tutorial)、[执行日志说明与截图](https://multica.ai/docs/tasks)、[任务模型](https://multica.ai/docs/issues)、[项目模型](https://multica.ai/docs/projects) 和 [Agent 模型](https://multica.ai/docs/agents)。这些来源显示：任务是长期上下文，Run 是一次执行；任务正文和讨论居中，属性与执行历史位于侧边；完整 transcript 在专用视图里展开。Multica 的分派通常触发运行，而 DSH 已确定 **分派与启动分开、单执行槽、人工验收**，下面的建议保留这三项产品约束。

这是一次有样本边界的专家走查，不是多人可用性实验。优先级按本次真实操作中的阻力、代码中的结构性问题和用户此前指出的“执行过程或记录难看懂”排序。

## 2. 总体结论

v0.6.0 已经有可用的核心闭环。工作台入口清楚，看板与列表都能进入任务；状态色和执行状态卡一致；Agent 消息与工具卡分层；长工具参数折叠；原始记录可追溯。GLM 的这一轮使“发生了什么”比早期版本清楚得多。

目前的主要阻力是 **信息虽完整，却仍以一个很长的任务抽屉串行呈现**：任务要求、分派、Run 状态、四个事实卡、三个视图、交付报告、证据、验收和讨论依次往下排。用户需要滚动和切换，才能把“任务现在要我做什么”和“这次 Run 具体做了什么”合在脑中。工作台的下一阶段应优先重排信息结构，再微调颜色和动效。

### 任务状态与 Run 状态的区别

实测任务当前为“待办”，但它的一次历史 Run 显示“执行完成”，讨论区还有过去的“验收通过”。这些事实可以同时成立：任务后来被重新打开。然而只有一次 Run 时，当前组件直接隐藏“执行历史”，用户看不到“上一次执行”的锚点，容易把历史 Run 的成功误读成任务已完成。这是当前最具体的语义混淆。

## 3. 与 Multica 的对照：借鉴结构，不照搬产品边界

| 体验维度 | Multica 公开界面/文档 | 当前 DSH | 建议 |
|---|---|---|---|
| 主页面 | 任务正文、活动/讨论为中央主线；右侧保留属性和 Execution log | 总览/看板之后，任务进入 880px 抽屉，所有内容纵向堆叠 | 任务详情改成工作台内的完整页面；中央放目标、讨论与交付，右侧固定属性与 Run |
| 执行入口 | 标题旁有“Agent is working”，右栏 Run 可直接进入 transcript | 执行状态卡在抽屉较下方，任务状态和 Run 状态相距较远 | 标题旁放运行状态及“查看执行”；右栏始终显示当前/最近 Run |
| 历史 Run | 活跃 Run 置顶，过去 Run 折叠，状态、Agent、时间可扫读 | 仅 `runs.length > 1` 时显示历史；一次 Run 无列表 | 从第 1 次 Run 就展示；统一“第 N 次／触发方式／状态／时间” |
| 执行详情 | 专用 transcript；时间/事件量、Focus、筛选、顺序切换；工具行可展开 | 抽屉内嵌的 72vh 活动滚动区，外面仍有抽屉滚动 | 用工作台内大幅 Run 视图或专用覆层；避免双层长滚动 |
| 交付与讨论 | Agent 的交付进入任务活动流；截图等内容可直接看；评论输入贴近活动 | 报告集中在“结果概览”，讨论在整个 Run 区域后方；证据只能复制路径 | 任务活动流展示简短交付卡和可预览证据；完整报告在 Run 视图 |
| 项目 | 项目承载目标、状态、资源和任务进度 | 当前项目面板主要是名称、路径、任务数 | 首版先补目标、最近活动、待处理数与进度；保持本机路径绑定 |

对照来源：[官方任务截图与教程](https://multica.ai/docs/tutorial)、[Runs](https://multica.ai/docs/tasks)、[Issues](https://multica.ai/docs/issues)、[Projects](https://multica.ai/docs/projects)。Multica 官方还明确区分 Run 完成与任务完成；DSH 应把这个区别写进界面，而不让用户从状态码自行推断。

## 4. 按真实使用路径的具体问题

### 4.1 总览：计数完整，但缺少“下一步”

**观察**：顶部五张统计卡很整齐，但样本只有一条待办任务时，四张都是 0；下方“当前项目”和“最近任务”占据较大面积，却没有提示下一步是配置 Agent、手动运行，还是人工验收。大幅空白在小数据量下尤其明显。

**优化**：

1. 顶部先放一条“现在需要你处理”的行动区，按 **待验收 → 受阻 → 正在运行 → 未分派待办** 排列；显示原因与单个主动作。空闲且无任务时显示三步引导。
2. 五状态计数保留为次级概览；零值压缩为一行轻量指标。点击某个状态后，任务页应只展示对应列表或对应列，避免进入看板后仍有四个空列。
3. 项目卡展示项目名称、工作区简写、待处理/执行中/待验收数量与最近活动。完整路径放在项目详情或悬浮提示，不要成为总览的主视觉。

**验收**：打开工作台后 5 秒内能判断“有没有任务需要我决定”；点击待验收卡后无需二次筛选即可看到待验收任务。

### 4.2 看板与列表：展示有了，操作暗示还不准确

**观察**：看板五列视觉上都像可拖入，但当前只有“待办”和“受阻”能手动互换；拖向执行中、待验收、完成会在释放后才弹出提示。状态筛选下仍渲染五列，空列占空间。卡片里展示 Agent 和 Run 数，但没有“下一步”。

**优化**：

1. 拖拽开始时直接把不可投放列标为禁用，并显示原因；可投放列强调边框。保留键盘状态选择。
2. 状态筛选在看板中只显示匹配列；“全部状态”才显示五列。零任务列可降低高度，让单项目视图更紧凑。
3. 卡片增加 **状态下一步**：未分派显示“分派 Agent”；已分派待办显示“待手动启动”；待验收显示“等待人工验收”；受阻显示简短原因。卡片正文只留 1–2 行预览。
4. 列表在“任务、项目、执行者、状态、Run”之外，加“更新于”和“下一步”，支持按待处理优先排序；不急于增加复杂字段和视图类型。

**验收**：用户拖动前就知道目标列是否可放；在看板上无需打开详情也能知道各任务下一步。

### 4.3 任务详情：应成为主要工作页面

**观察**：当前抽屉宽 880px，盖住一部分原页面；用户在抽屉里完成编辑、运行、读记录、讨论、验收。Run 内的活动区又独立滚动，形成双层滚动。标题、当前任务状态、历史 Run 状态和验收动作无法同时进入视野。

**建议目标布局**（DSH 自有视觉，不复制 Multica 代码）：

```text
┌ 左侧主导航 ┬────────── 任务主区域 ──────────┬── 固定信息栏 ──┐
│ 总览/任务  │ 返回项目  任务标题  [任务状态] │ 项目 / 工作区   │
│ 项目/Agent │ 任务目标与验收标准             │ 执行者 / 模型   │
│            │                               │ 单执行槽状态   │
│            │ 活动流：讨论、进度、交付卡     │ [手动运行]     │
│            │ [评论输入，靠近最新活动]       │ 当前/历史 Run  │
│            │                               │ 验收操作       │
└────────────┴───────────────────────────────┴─────────────────┘
```

在 1280px 宽时右栏可以收窄；小屏时信息栏变为可展开区域，任务正文优先。保留抽屉作为看板里的“快速查看”，点击“打开完整任务”进入上面的页面。这样既有看板快速扫描，也有稳定的工作区供阅读和验收。

**关键规则**：

- 页头同时显示 **任务状态** 与 **当前/上次 Run 状态**，明确写“上次执行完成”而非笼统“本次执行完成”。即便只有一次 Run，右栏也展示该 Run。
- “分派 Agent”是配置动作；“手动运行”是单独的主按钮。执行槽被占用时按钮禁用并说明占用任务，而非让用户点击后才收到冲突。
- 验收按钮固定在信息栏底部或任务页的交付卡旁；审核时不需要滑到长页面底端。接受与退回都指向当前待验收 Run，避免用户在切换历史 Run 后误判。
- 任务目标及验收标准默认可见一段摘要，可一键展开；编辑入口放在标题附近。内部 ID、revision、原因码继续收在“技术信息”。

**验收**：从看板进入任务后，屏幕内能同时看到任务状态、Agent、最近 Run、主动作；1200px 宽视口下无需横向滚动；验收操作无需滚过完整日志。

### 4.4 执行过程：从“事件可读”提升到“过程可扫读”

**观察**：现在 9 条活动能区分 Agent 消息与工具卡，长参数被折叠，已比旧版明显进步。但工具卡等高、信息密度小；完成一次简单任务仍要在内外两个区域滚动。活动筛选后显示数已在当前工作区改为“显示 3 / 9 条”。对于更长的 Run，单纯线性卡片会继续变长。

**优化**：

1. 用专用的 Run 阅读视图承载完整 transcript：顶部固定状态、Agent、开始时间、耗时、事件量；中部是事件流。参考 Multica 的 **Focus／筛选／顺序切换** 交互，但采用 DSH 自有组件和颜色。
2. 默认视图聚焦 **Agent 叙述、进度、错误和关键工具结果**；“全部事件”仍完整可达。每条工具行先显示工具名、目标文件/路径或摘要、成功/失败、时间；参数和原始返回次级展开。
3. 工具调用与结果继续合并为一条；连续同类工具可折成“写入报告 ×2”，但必须能展开到每条原始事件。不要伪造完成百分比或隐藏失败。
4. 增加事件顺序切换与“跳到最新”，保留用户滚离底部时的新事件浮标。关闭/重开视图后记住筛选与滚动位置，避免重复找上下文。
5. 事件数量多时需要真正的分页或虚拟列表，并保持原始 seq、时间和展开内容可追溯。原始记录是审计层，默认无需占据主阅读路径。
6. 状态使用中文可操作说明：例如“等待子代理停止”“工作区被另一任务占用”，在附近给对应操作或说明，不只给内部阶段名。

**验收**：在 50 条以上事件中，用户能快速定位最近 Agent 说明、失败工具和最终交付；切换筛选不丢阅读位置；历史 Run 不触发新执行。

### 4.5 报告、证据与人工验收：让产物成为页面主角

**观察**：样本 Run 的报告是一整段约 500 字文本；两个真实文件只在下方列路径与“复制路径”。文件都存在，但要离开工作台、粘贴路径才能看内容。报告讲了很多过程与内容，用户要自行找“交付什么、在哪里、是否满足验收”。

**优化**：

1. 结果概览固定四块，顺序为：**结论与待处理问题 → 交付物 → 对照验收标准 → 完整报告/技术信息**。已有字段不足时保留“未提供”，不根据模型长段落自动猜测通过。
2. 交付物卡显示文件名、类型、大小、路径摘要、可用动作。文本/Markdown/图片/PDF 提供安全预览；HTML 等可执行内容只在隔离预览中打开，不注入 DSH 主页面；所有读取仍经服务端工作区实路径校验。
3. 新 Run 可增加结构化交付字段（标题、文件引用、摘要、未完成项），但必须兼容旧 Run：旧报告先只按段折叠、置顶证据，不自动改写历史数据。
4. 人工验收区紧邻交付物：显示标准清单、接受/退回按钮和退回意见。接受后记录具体 Run 与时间；重新打开任务时这条历史验收仍可查看，但不冒充当前任务状态。
5. 讨论输入应靠近任务活动流最新位置。进度和系统事件默认压缩，评论、Agent 最终交付和人工决定保持展开。避免把 Run 过程与任务讨论各完整复制一次。

**验收**：任务交付后，用户在工作台内 1 次点击可打开主要产物；能看出哪些验收条件有证据、哪些仍需人工判断；不读完整 500 字报告也能找到结论和文件。

### 4.6 项目、Agent 与创建流程

- **项目**：创建时目前要手输本机绝对路径。优先对接 DSH 已有工作区列表作为候选，并实时显示服务端路径校验结果；保留手输路径。项目页补目标、状态、待办/受阻/待验收数和最近任务；不急于搬进 Multica 全套日期、优先级和仓库资源。
- **Agent 目录**：现在能看到模型、工具数和指令，建议加清楚的角色描述与“该 Agent 能做什么”摘要，工具权限以人话显示；详情中展示其最近 Run 与受阻原因。不要显示无法由宿主证明的“在线”状态。
- **任务创建**：表单已能一次填项目、描述、标准和 Agent，但“分派后不会自动运行”应在 Agent 选择附近常驻说明；保存后给明确下一步“任务已创建 → 手动运行”。

## 5. 视觉语言：向 Multica 的清晰度靠近，保持 DSH 身份

Multica 官方截图的可取之处是 **留白、标题与正文的层级、窄右栏的常驻属性、低噪声的系统信息，以及交付内容直接进入阅读区**。它并非靠更多状态色或动效显得清楚。当前 DSH 暗色工作台已有一致的颜色基调，接下来应减少同等权重的边框和卡片，让主次更明显。

| 元素 | 建议 |
|---|---|
| 背景层次 | 主阅读区用稳定底色；只有可交互、需要决策或代表产物的内容放卡片。减少“卡片套卡片”。 |
| 文字 | 标题 22–26px、区块标题 16–18px、正文 13–14px、元信息 11–12px；正文行高约 1.6，长报告限宽约 70–80 字符。当前 10–11px 的路径与事件元信息可适度提高。 |
| 状态色 | 颜色只增强文字状态：执行中蓝、待验收琥珀、受阻红、完成绿；同时保留文字和图标，不以颜色单独传达含义。 |
| 按钮 | 每屏一个主动作；任务页主动作随状态变为“手动运行”或“验收”。编辑、复制、技术信息退为次级操作。 |
| 动效 | 保留抽屉/弹窗进入反馈；列表与日志不要每次轮询都重新做入场动画。继续尊重 reduced motion。 |
| 宽屏与窄屏 | 宽屏三栏；窄屏正文优先，属性栏可唤出。图标化导航在窄屏须有悬浮提示与可见选中状态。 |

视觉上可贴近 Multica 的 **信息密度、内容宽度与层级关系**，不复制其标识、截图资源或 UI 源码。当前 [Multica License](https://github.com/multica-ai/multica/blob/main/LICENSE) 对衍生自其 UI 代码的界面保留品牌与署名条件；这里建议借鉴产品模型和公开页面中的通用布局原则，继续实现 DSH 自有界面。该段是实现边界提示，不替代正式许可证审查。

## 6. 推荐实施顺序

| 顺序 | 改动 | 用户收益 | 验证重点 |
|---|---|---|---|
| P0 | 始终显示第 1 次 Run；页头分开任务状态与上次 Run 状态；总览给出下一步 | 消除“待办但执行完成”的歧义 | 重新打开、接受、退回、取消后状态文案正确 |
| P0 | 交付物一键安全预览；报告改为结论/文件/待判断项优先 | 验收最快见效 | 路径越界拒绝、HTML 隔离、旧 Run 兼容 |
| P1 | 完整任务页面 + 常驻属性/Run 右栏；看板抽屉变快速查看 | 少滚动、上下文稳定 | 1280/1024/768px、键盘焦点、刷新后定位 |
| P1 | 专用 Run 阅读视图，工具摘要、过滤、顺序切换、跳最新 | 长执行记录可扫读 | 50/500 条事件、分页、滚离底部、新事件 |
| P1 | 看板拖放前提示合法目标；筛选后隐藏无关列 | 操作预期明确 | 鼠标和键盘路径一致 |
| P2 | 项目页和 Agent 目录摘要、创建后下一步引导 | 减少表单试错 | 无项目、无 Agent、单执行槽忙碌等空/边界状态 |
| 后续里程碑 | 小队与自动化 | 扩大工作范围 | 等核心任务页与 Run 阅读体验稳定后再叠加 |

当前工作区已修复一次真实走查中发现的“任务要求卡随 5 秒刷新反复增加”问题，并将活动筛选数显示为“显示 N / 总数”。这两处是代码改动，不属于本报告后续设计建议。对应构建与 72 项插件测试已通过；尚未提交。

## 7. 建议的端到端验收脚本

使用隔离 DSH 实例和不含 trajectory 的工作区，准备至少 **3 个任务、2 个 Agent、1 个长 Run、1 个失败或受阻 Run、1 个经退回后再次运行的任务**。逐项验证：

1. 新用户从总览创建项目/Agent/任务，分派后仍未自动运行；下一步提示明确。
2. 单执行槽空闲与忙碌时，手动运行按钮的状态和理由正确。
3. 运行中查看 Agent 消息、工具摘要与原始事件；滚离底部不会被强制拉回，有新事件提示。
4. 完成后在任务页面直接打开安全预览，核对报告与证据，再接受或退回。
5. 退回并第二次运行后，两次 Run 均保留；任务状态与每次 Run 状态在标题、列表、历史中一致。
6. 重新打开一个已验收任务时，旧 Run 标为历史；旧的“验收通过”不会显示成当前完成状态。
7. 1280、1024、768px 和 200% 缩放下，主动作、Run 入口、证据和讨论可达；全流程键盘可操作。
